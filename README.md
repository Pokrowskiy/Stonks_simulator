## Архитектура: Модульный монолит
Система запускается как единый процесс, где модули разделены логически, но имеют прямой доступ друг к другу через внутренние интерфейсы. Оркестратор (Main Loop) управляет временем и синхронизацией.
### Стек технологий
* **Бэкенд & Оркестратор:** Python 3.11+ с `FastAPI` (предоставляет REST API для управления и WebSockets для передачи потоковых данных на фронт без задержек).
* **Математика рынка:** `NumPy` (для генерации шума и расчетов стакана).
* **Фронтенд (Дашборд и Стрим):** HTML/JS + `TradingView Lightweight Charts` (самая производительная библиотека для отрисовки биржевых свечей и графиков в вебе).
* **Асинхронность:** Встроенный `asyncio` для работы тикера параллельно с API-сервером.

Симуляция исчисляется тиками. Каждый тик считается за час, один цикл - одна неделя или 168 тиков.

## Модуль: Market Engine (Движок рынка)
**Зона ответственности:** Хранение фундаментальных данных компаний, расчет их котировок на основе спроса и предложения, обработка новостного фона и управление жизненным циклом дивидендов.
### 1. Структура актива (Модель Компании)
Каждая компания в симуляции должна представлять собой объект со следующими группами атрибутов:
| Блок | Параметры | Описание |
| --- | --- | --- |
| **Идентификация** | `name`, `description`, `sectors` | Название, лор и массив отраслей (например, `["Tech", "Hardware"]`). Массив нужен, чтобы глобальные новости били по смежным сферам. |
| **Рынок** |  `price`, `volatility`, `price_history` | Текущая цена, коэффициент резкости изменения цены и массив с историей (для графиков и загрузки в ИИ-Аналитика). |
| **Фундаментал** | `profit_base`, `profit_growth`, `previos_div_profit` | Базовая прибыль, шаг ее постепенного роста/падения за тик и значение в момент предыдущей выплаты дивидентов. На рост накладывается математический шум для естественности. |
| **Дивиденды** | `div_payout_ratio`, `div_period` | Процент **от текущей прибыли**, идущий на выплату, и интервал (например, каждые 168 тиков). |

Также есть особая компания - индекс биржи. Её невозможно купить или продать, а цена считается как средняя стоимость всех акций. Служит исключительно для аналитики.
### 2. Система ивентов (News & Events)
Ивенты — это объекты, которые временно вмешиваются в математику рынка. Они могут таргетироваться на конкретный тикер, на весь сектор (через проверку совпадений в массиве `sectors`) или на весь рынок целиком.
Настройки каждого ивента:
* **Target (Цель):** Компания, сектор или глобальный индекс.
* **Impact (Сила влияния):** Может влиять на *объем стакана* (вызывает панику или эйфорию покупателей) или напрямую на *прибыль компании* (например, новость "Сгорел завод" урезает `profit_base`).
* **Duration (Длительность):** Сколько тиков живет новость.
* **Decay (Затухание):** Функция спада эффекта. Новость может быть *линейной* (эффект равномерно падает до нуля) или *шоковой* (весь эффект выплескивается в первые несколько тиков).
### 3. Механика торгов и дивидендов
Чтобы график выглядел органично, движок учитывает реальные рыночные правила:
* **Дивидендный гэп:** В тик выплаты дивидендов стоимость акции принудительно обваливается на сумму выплаты на одну акцию. Это железное правило рынка: деньги ушли со счетов компании инвесторам, капитализация компании уменьшилась.
* **Естественное восстановление:** Если фундаментальная прибыль компании стабильно растет, то после гэпа подешевевшая акция становится привлекательнее для виртуальных инвесторов (увеличивается базовый спрос в стакане). Цена начинает органично отрастать обратно без искусственных костылей в коде.
### 4. Сохранение и загрузка состояния (State Management)
Симуляция не должна сбрасываться при перезапуске скрипта или краше стрима.
* **Auto-Save:** В основном цикле (Main Loop) стоит счетчик тиков. Каждые 24 тика (конец виртуальных суток) движок собирает всю информацию — цены, историю, текущие прибыли, таймеры дивидендов и оставшееся время активных новостей — и сериализует это в `state.json`.
* **Load (Hydration):** При запуске сервера скрипт проверяет наличие файла `state.json`. Если он есть, движок загружает все параметры и продолжает работу с того же тика, на котором остановился. Если файла нет — генерирует стартовые условия из start_config.json

## Модуль: Broker (Брокерская система)

**Зона ответственности:** Управление счетами множества пользователей, обработка API-заявок на покупку/продажу, расчет маржинального обеспечения по системе УДС и проведение ликвидаций (маржин-коллов). Имеет систему сохранения состояния аналогичную предыдущему, но другие файлы сохранений.

### 1. Модель инвестиционного счета

Брокер работает как словарь (хэш-таблица), где ключом выступает `username` (например, "Mint_AI", "Admin", "Viewer_1"), а значением — объект портфеля.

| Блок | Параметры | Описание |
| --- | --- | --- |
| **Идентификация** | `username` | Уникальное имя владельца счета. Позволяет торговать не только Минт, но и другим агентам (или зрителям). |
| **Активы** | `cash_balance` | Свободные деньги. Может быть отрицательным (если куплено в лонг с плечом, то есть деньги взяты в долг у брокера). |
|  | `positions` | Словарь активов `{"GigaTech": 15, "PowerCorp": -10}`. Положительное значение — лонг, отрицательное — шорт (акции взяты в долг). |
| **Аналитика** | `start_value` | Стоимость портфеля на момент создания счета (для расчета глобальной доходности). |
|  | `day_start_value`<br>

<br>`week_start_value` | Стоимость портфеля на начало текущих виртуальных суток и недели. |
|  | `portfolio_history` | Массив значений стоимости портфеля, который пополняется каждый виртуальный день. |

### 2. Математика портфеля и маржи

Для расчета УДС брокеру на каждом тике необходимо вычислить три базовые метрики для каждого счета.

**1. Стоимость портфеля (Эквити):**
Текущая реальная ценность всех активов пользователя.


$$Portfolio\_Value = Cash\_Balance + \sum_{i=1}^{n} (Position\_Size_i \cdot Current\_Price_i)$$


*(При шорте размер позиции отрицательный, поэтому рост цены акции будет уменьшать стоимость портфеля, что математически верно).*

**2. Начальная маржа (Initial Margin):**
Сколько собственных средств нужно для удержания текущих позиций. Зависит от ставки риска актива (ликвидные акции требуют меньше маржи, волатильные — больше).


$$Initial\_Margin = \sum_{i=1}^{n} (\vert{}Position\_Size_i\vert{} \cdot Current\_Price_i \cdot Risk\_Rate_i)$$

**3. Минимальная маржа (Min Margin):**
Критический уровень, по достижении которого брокер закрывает позиции.


$$Min\_Margin = \frac{Initial\_Margin}{2}$$

### 3. Логика УДС (Уровень достаточности средств)

На основе трех метрик выше брокер рассчитывает УДС по формуле:


$$УДС = \frac{Portfolio\_Value - Min\_Margin}{Initial\_Margin - Min\_Margin}$$

Результат жестко ограничивается (clipping) в диапазоне `[-9.99, +9.99]`.

**Режимы состояния счета (State Machine):**

* **УДС > 1 (Зеленая зона):** Обеспечения достаточно. Пользователь может свободно открывать новые позиции (в том числе с плечом) и выводить кэш.
* **УДС = 1:** Стоимость портфеля в точности равна начальной марже.
* **0 < УДС ≤ 1 (Желтая зона / Margin Warning):** Стоимость портфеля упала ниже начальной маржи. API Брокера начинает блокировать заявки на открытие новых позиций. Разрешено только:
* Закрывать текущие сделки (уменьшая требуемую маржу).
* Пополнять `cash_balance`.
* Ждать роста стоимости активов.


* **УДС ≤ 0 (Красная зона / Margin Call):** Стоимость портфеля опустилась ниже минимальной маржи. Брокер принудительно обнуляет словарь `positions`, фиксирует убыток в `cash_balance` и генерирует событие ликвидации для трансляции на стрим.

### 4. Внешний API (Управление заявками)

Модуль предоставляет эндпоинты для приема сообщений (например, через FastAPI).

**Пример POST-запроса `/broker/order`:**

```json
{
  "username": "Mint_AI",
  "ticker": "GigaTech",
  "action": "BUY",
  "quantity": 100
}

```

**Логика обработки заявки (Order Execution):**

1. Брокер симулирует исполнение заявки (меняет `cash_balance` и `positions`).
2. Рассчитывает гипотетический УДС с учетом новой позиции.
3. Если гипотетический `УДС > 1`, сделка одобряется, состояние счета обновляется.
4. Если гипотетический `УДС <= 1`, брокер отклоняет заявку (отдает ошибку: *"Недостаточно обеспечения для сделки"*).

### 5. Интеграция с циклом времени (Срез аналитики)

В связке с Market Engine, Брокер реагирует на прохождение времени:

* **Конец дня (например, каждые 24 тика):** Брокер фиксирует текущий `Portfolio_Value` каждого пользователя, добавляет его в массив `portfolio_history` и обновляет `day_start_value`. Это необходимо для того, чтобы ИИ-Аналитик мог принимать решения, основываясь на дневном тренде, а зрители в вебе видели красивый PNL (Profit and Loss) за сегодня.
* **Конец недели (168 тиков):** Обновляется `week_start_value`.
* **Удержание позиций:** Раз в сутки с `cash_balance` может списываться микро-комиссия брокера
